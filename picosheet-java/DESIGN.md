# Picosheet 設計メモ（0.2.0 の作り直し）

0.2.0 で作り直す部分について、決めたことと、その理由、まだ決めていないことを残す資料です。人もAIも参照します。
問題の一覧は [TODO.md](TODO.md) にあります。本文の「#30」などは TODO.md の番号です。

## 使い方
- 決めたことは「決定事項」に、決めた日付と理由と一緒に書きます。理由は、後から見直すときに一番必要になる情報なので、省略しません。
- 決めたことを変えるときは、元の内容を消さずに「（YYYY-MM-DD に変更）」と書き、新しい内容と理由を書き足します。
- まだ決めていないことは「未決定事項」に書きます。決めたら「決定事項」に移します。
- 作り直しが終わったら、利用者向けの内容は [AI_REFERENCE.md](AI_REFERENCE.md) に反映します。

## 1. 基本方針

### 1.1 公開APIの互換は保たない（2026-11-15）
0.2.0 はまだ公開しておらず、ライセンスも変えたばかりなので、公開APIを作り直すのに一番よい時期です。
式の解析のうち字句に分ける部分（`FormulaParser.split`）と、依存関係の追跡（`Resolver` の参照の表と、「計算必要」の印を付けてから必要なセルを計算する仕組み）は残します。

### 1.2 ルールは Excel に準ずる（2026-11-15）
式の書き方や計算のルールは、できるだけ Excel と同じにします。Excel から外れる場合は、その理由をこのメモに書きます。

**理由**
- 利用者も AI も、スプレッドシートの知識のほとんどが Excel のものです。Excel と同じ形の式が黙って違う結果を返すと、気づかずに間違えます。
- スプレッドシートには共通の標準ルールがありません。OpenDocument の数式の規格（OpenFormula）は、型の違う値どうしの比較の結果を「実装が決める」としています。LibreOffice Calc は論理値を数値として扱い、Excel と違う結果になります。どこかに合わせるなら、利用者と AI の知識に一番近い Excel が適しています。

**Excel に合わせるもの**（今の Picosheet と違うもの）

| 内容 | Excel の動き | TODO |
|---|---|---|
| 型の違う値の比較 | 数値 < 文字列 < 論理値の順に比べる（`TRUE<9` は `FALSE`） | #17 |
| 空のセル | `empty=0` も `empty=""` も `TRUE` | #17 |
| 文字列の比較 | 大小比較ができる。大文字と小文字は区別しない | #16 |
| 文字列リテラルの比較 | `"a"="a"` と書ける | #15 |
| 演算子の優先順位 | `^` は `*` `/` より先。単項の `-` は `^` より先（`=-2^2` は 4） | #14 |
| 比較演算子 | 二項演算子として左から順に計算する（3.4 を参照） | |
| 関数名 | 大文字と小文字を区別しない | #6 |
| エラーの伝わり方 | 最初に起きたエラーの種類を保つ。`SUM` なども引数のエラーを返す。範囲の中は行ごとの順で見る（2.6 を参照） | #11、#12 |
| 論理値の数値としての扱い | `TRUE+1` は 2。`SUM` などの集計では、範囲の中の論理値は無視する（引数に直接書いた `TRUE` は数える） | |
| エラーの種類 | `#DIV/0!`、`#REF!`、`#NAME?`、`#VALUE!`、`#N/A`、`#NUM!` などと対応させる | #35 |
| `AND`・`OR` | 結果が決まっても後ろの引数を計算する。`=AND(FALSE,1/0)` は `#DIV/0!`（2.6 を参照） | #11 |
| 循環参照の判断 | 計算するときに実際に読んだ参照で判断する。`IF` の使わない側を通る循環は循環にならない（3.8 を参照） | #32 |
| 算術演算での文字列 | 数値として読める文字列は数値にする（`"1"+1` は 2）。読めなければ `#VALUE!`（`"a"+1`、`""+1`）。前後の空白は無視する | |
| 論理値を文字列にしたとき | `"TRUE"` と `"FALSE"`（`TRUE&""` は `"TRUE"`） | |

**Excel に合わせないもの**

| 内容 | Picosheet | 理由 |
|---|---|---|
| 数値の精度 | `BigDecimal` で計算する（`0.1+0.2` が `0.3` になる） | Picosheet の利点なので残す。Excel は浮動小数点（有効数字15桁） |
| セルの参照 | 名前で参照する（`A1` 形式は使わない） | Picosheet の中心となる考え方。名前のほうが人も AI も式を正しく読み書きできる |
| 数値として読める文字列の範囲 | `BigDecimal` で読める形だけ（`"1.5"`、`"-2"`、`"1e3"` など）。`"1,000"`、`"50%"`、`"$1"`、日付の文字列は読まない | Excel の読み方は地域の設定で変わり、決まりが複雑。必要になったら足す |
| 数値を文字列にしたとき | 指数表記を使わず、末尾の0を付けない（`1.50&""` は `"1.5"`、`10^20&""` は `"100000000000000000000"`） | Excel は有効数字15桁までで、大きい数や小さい数は指数表記（`1E+20`）にする。Picosheet は `BigDecimal` の桁をすべて残す |
| 循環しているセルの値 | 循環参照のエラーにする（3.8 を参照） | Excel は警告を表示して前の値（多くは 0）を残す。Picosheet はライブラリで、警告を見る画面がない。黙って値を返すと、利用者も AI も誤りに気づけない |

## 2. 値・式・関数の引数を分ける（#30）

### 2.1 今の `Element` の問題（2026-11-15 に調査）
`Element` は、次の4つの役割を1つのクラスで兼ねています。

| 役割 | `ElementType` | 使う側 |
|---|---|---|
| セルの値 | `EMPTY` `NUMBER` `STRING` `BOOLEAN` `DATE` `ERROR` | 利用者（public） |
| 式の部品 | `OPERATOR`（括弧・カンマ・`USE_LAST_RVALUE` も含む）、`FUNCTION` | `FormulaParser`、`Calculator` |
| 参照（名前の文字列） | `REFERENCE` `GROUP_REFERENCE` `TABLE_REFERENCE` | 式の部品。関数の引数として計算前のまま関数にも渡る |
| 計算途中の値 | セルの値と同じ | `Calculator` の計算用スタック |

このために、次の問題が起きています。
- 利用者が値を `switch` で取り出すとき、値になり得ない `OPERATOR` なども出てくる。
- 関数がセルの名前と `Resolver` を受け取り、自分で参照を解決している。エラーの扱いが関数ごとにばらばらになり、#11 の原因になっている。関数からブック全体に手が届く。
- 型の変換が暗黙に行われる（`getNumber()` が空・論理値・日付でも値を返す）。変換の決まりが1か所にまとまっていない。

ほかに見つけたこと：
- `Element.newElement(ElementType.BOOLEAN)` は `case` に `break` がなかったので、必ず例外になっていた（2026-11-15 に `break` を追加）。

### 2.2 3つに分ける（2026-11-15）

| 区分 | 公開 | 内容 |
|---|---|---|
| 値 | 公開 | セルの値、計算途中の値、関数の戻り値 |
| 式 | 内部 | 字句に分けた結果と、解析したあとの式 |
| 関数の引数 | 公開 | 計算の側（エンジン）が参照を解決した結果。`Value` 1つか、`Value` の並び（範囲） |

### 2.3 値は不変の sealed interface と record で表す（2026-11-15）

```java
public sealed interface Value {
    record Empty()                  implements Value {}
    record Number(BigDecimal value) implements Value {}
    record Text(String value)       implements Value {}
    record Bool(boolean value)      implements Value {}
    record Date(...)                implements Value {}   // 型は未決定（4.1）
    record Error(ErrorKind kind, ...) implements Value {} // 持たせる情報は未決定（4.4）
}
```

- 種類の漏れはコンパイラが見つけられる。
- 型の変換（空を 0 として扱う、など）の決まりは1か所にまとめ、1.2 の方針で Excel に合わせる。

### 2.4 全体共通の Element キャッシュはなくす（2026-11-15）
今の `Element` は、同じ値のインスタンスを共有するために、static な `WeakHashMap<Element, Element>` のキャッシュを通しています。
元の狙いは、大きなテーブルで空のセルの値を大量に作る無駄を省くことでした。

**なくす理由**
- **メモリが解放されない**：`WeakHashMap` が弱く参照するのはキーだけで、値は強く参照します。今はキーと同じオブジェクトを値に入れているので、エントリーがいつまでも回収されません（`WeakHashMap` の Javadoc にも注意書きがあります）。実際に、Element を10万個作って参照を捨て、GC を5回実行しても、キャッシュの件数は10万のままでした。値を100万回入れ替えると約80MB増え、ブックを捨てても減りませんでした。
- **全体で1つのロックを取り合う**：`newElement` が static で `synchronized` なので、ブックが別でも同じロックを取り合います（#31）。
- **共有の効果が小さい**：計算結果の数値や文字列は値がばらばらで、共有されることはほとんどありません。

**元の狙いの守り方**
- 空・`TRUE`・`FALSE` は定数を1つずつ持ち、共有する。大きなテーブルの空のセルは、すべて同じ1つのインスタンスを指す。
- ほかの値を共有したくなった場合は、`Integer.valueOf` のように、よく使う小さい範囲だけを定数として持つ。

### 2.5 関数には解決済みの値を渡す（2026-11-15、方向のみ）
- 関数は参照の名前と `Resolver` を受け取らない。範囲（グループ・テーブル）は値の並びとして受け取る。
- 引数にエラーがあれば、関数を呼ぶ前にエンジンがエラーとして返す。`IFERROR` のようにエラーを受け取りたい関数だけ、そう宣言する。こうすれば #11 は関数の作り方に関係なく起きない。
- 関数に何を見せるか（API の形）は 2.6 で決めた（2026-11-27）。

### 2.6 関数の API（2026-11-27）
2.5 の方向を、次の形にします。

```java
@FunctionalInterface
public interface Function {            // 名前は今の Function と重なるので、作るときに決める
    Value apply(List<Argument> args, FunctionContext context);
}

public sealed interface Argument {
    record Single(Value value) implements Argument {}
    non-sealed interface Area extends Argument {   // テーブルの範囲。行と列の形と、行ごとの順を持つ
        int rows();
        int columns();
        Value get(int row, int column);            // 1 始まり（Range.getCell と同じ）
    }
    non-sealed interface Bag extends Argument {    // グループ。形も順序も持たない
        int size();
        Iterable<Value> values();
    }
}

public interface FunctionContext {
    MathContext mathContext();
}
```

**引数と文脈**
- 関数が受け取るのは、計算済みの引数と `FunctionContext` だけ。参照の名前・`Resolver`・セルは受け取らない。
- 引数は、値1つ（`Single`）、テーブルの範囲（`Area`）、グループ（`Bag`）のどれか。`SUM` などで「範囲の中の論理値は無視し、引数に直接書いた `TRUE` は数える」（1.2 の表）を守れるように、値1つと範囲を区別する。
- 範囲を関数の引数以外で使った場合（`=グループ名` だけの式など）は `#VALUE!` にする。
- `FunctionContext` は、今は `MathContext` だけを持つ。あとで渡すものが増えても、公開した形を変えずに済む。
- 関数は状態を持たず、副作用を持たない（3.8 の並列化、#31）。

**範囲の引数**
- 範囲の引数は、関数を呼ぶ前にエンジンが作る、その時点の値の写し。関数には `Cell` も今の `Range` も渡さない。`Cell` を読むと、参照から値を得る口（3.8）を通らないので、計算していないセルの古い値を読んだり、循環参照や引数のエラーを見落としたりする。
- 範囲の中に「計算必要」のセルがあれば、参照から値を得る口がまとめて `NotYetCalculated` で知らせる（3.8）。写しを作るのは、範囲の中がすべて計算済みになってから。
- 写しを作る間に値が変わらないよう別のロックを持つ必要はない。再計算は書き込みと同じスレッドで、書き込みの操作の中で行われ、複数のスレッドから使う場合は `ConcurrentBookWrapper` がブック全体を守っている。計算を別のスレッドで進める形（#27、3.8 の並列化）にするときに、ロックをあらためて考える。
- `Area` は、今の `Range`（テーブルの一部または全部）から作る。形と並び順は `Range` と同じにする。
- `Area` の値を順に見るときは、行ごとの順（左から右、上から下。`Range.getCells()` と同じ）にする。Excel も範囲の中のエラーをこの順で見る（2026-11-27 に確かめた。C5=11、D5=`#DIV/0!`、C6=`#N/A`、D6=`#DIV/0!` で `=SUM(C5:D6)` は `#DIV/0!`。列ごとの順なら `#N/A` になる）。
- `Bag` は、グループから作る。グループは順序を持たないことが特徴なので、写しにも順序を持たせない。
- `Area` と `Bag` をインターフェースにして、中身の持ち方は外から見せない。最初は、セルが持つ `Value` への参照を配列に写す実装にする。`Value` は不変なので値そのものは写さず、増えるのは参照の配列だけ（100万セルで約 4MB。関数が値を返せば捨てられる）。累計の列のように広い範囲を何度も写す場合に、測って問題になれば、写さない実装に差し替える。関数の作り方は変わらない。

| 関数の種類 | テーブルの範囲（`Area`） | グループ（`Bag`） |
|---|---|---|
| `SUM`・`COUNT` など、順序で結果が変わらない | 使える | 使える |
| `TEXTJOIN` など、順序で結果の並びが変わる | 行ごとの順 | 使えるが、並びは決まらない |
| `SUMIF` の `sum_range`・`VLOOKUP`・`MATCH` など、位置に意味がある | 使える | `#VALUE!` |
| 範囲に種類の違うエラーが複数ある | 行ごとの順で最初のエラー | どのエラーが返るかは決まらない |

**登録**
- ブックごとに1つの関数の一覧（仮に `FunctionRegistry`）を持つ。組み込みの関数は最初から登録しておく。`Book` と `Calculator` が別々の一覧を持つ今の形はやめる（#34）。
- ラムダやクラスで登録できる公開 API にする（#21）。リフレクションと `BuiltinFunctionsConstants` はやめる。
- 関数名は大文字と小文字を区別しない（`Locale.ROOT` で大文字にして持つ。#6）。
- 登録するときに、引数の種類を位置ごとに指定し、エラーを受け取るかを指定する。関数の中身の形は、どちらでも同じ。
- 引数の種類は次の4つ。省略できる引数と、最後の種類を繰り返せること（`SUM(...)` など）も指定できる。引数の個数の範囲は、ここから決まる。

| 種類 | 受け付けるもの | 例 |
|---|---|---|
| 値 | `Single` | `SQRT` の引数、`SUMIF` の `criteria` |
| テーブルの範囲 | `Area` | `SUMIF` の `range`・`sum_range`、`VLOOKUP` の表 |
| 範囲 | `Area` か `Bag` | `COUNTIF` の `range` |
| 何でも | `Single`・`Area`・`Bag` | `SUM`・`COUNT` の引数 |

- 種類が合わなければ、関数を呼ばずに `#VALUE!` にする（値の位置に範囲、テーブルの範囲の位置にグループ、など）。関数は、指定した種類の引数だけを受け取る。
- 範囲を受け付ける位置（テーブルの範囲・範囲・何でも）にセル1つの参照を書いた場合は、1行1列の `Area` にする。リテラルや計算の結果（`SUMIF(1, ">0")`）は `#VALUE!`。Excel もセルの参照は1行1列の範囲として受け付け、リテラルは受け付けない。エンジンは引数の `Expr` が参照かどうかを知っているので区別できる。
- 「何でも」の位置でもセル1つの参照を `Area` にするので、`SUM` の「範囲の中の論理値は無視し、引数に直接書いた `TRUE` は数える」（1.2 の表）は、セルの参照で渡した `TRUE` も無視することになる。Excel と同じ結果になる（2026-11-27 に確かめた。`=SUM(TRUE)` は 1、A1 が `=TRUE()` のとき `=SUM(A1)` は 0）。
- 関数名は、解析するときではなく計算するときに探す。見つからなければ `#NAME?`。あとから登録しても、再計算すれば直る。
- 引数の個数が合わなければ、関数を呼ばずに `#VALUE!` にする。Excel は式を入力するときに受け付けないが、Picosheet では関数の一覧があとから変わるので、計算するときに判断する。

**エラーの扱い**
- エラーを受け取ると指定しない関数は、引数（範囲の中も含む）にエラーがあれば呼ばれず、左から見て最初のエラーが結果になる。これで #11 は、関数の作り方に関係なく起きない。
- `ISERROR`、`COUNT` などのエラーを受け取る関数だけ、登録するときにそう指定する。
- `SUMIF`・`COUNTIF` なども、エラーを受け取る関数にする。Excel の `SUMIF` は、範囲の中で条件に合わないエラーを無視する（2026-11-27 に Excel で確かめた。範囲が `11, 22, #DIV/0!` で条件が `"<25"` なら 33、`#DIV/0!, 22, #DIV/0!` なら 22）。条件に合う行の `sum_range` がエラーなら、そのエラーを返す（`range` が `11, 22, #DIV/0!`、`sum_range` が `101, #DIV/0!, 305` なら `#DIV/0!`。同じ日に確かめた）。

**遅延評価の関数**
- `IF`、`IFERROR`、`IFNA`、`CHOOSE` など、引数を必要な分だけ計算する関数は、パッケージの中だけの別の形（引数の `Expr` を計算する口を受け取る）で作る。組み込みの関数だけに使い、公開しない。
- `AND`・`OR` は遅延評価にせず、ふつうの関数として作る。Excel では後ろの引数も計算し、`=AND(FALSE,1/0)` も `=OR(TRUE,1/0)` も `#DIV/0!` になる（2026-11-27 に Excel で確かめた）。

**理由**
- **公開する API を小さくする**：利用者が作る関数は、計算済みの値を受け取って値を返すだけになる。エラーの扱いや参照の解決を関数ごとに書かなくて済む。
- **遅延評価は外に出さない**：3.8 で、循環参照は実際に読んだ参照で判断すると決めた。`IF` の使わない側を計算すると、Excel と違う結果になる。遅延評価の関数は自分で引数を計算するので、エラーの扱いを関数ごとに書くことになり、公開すると #11 がまた起きうる。必要になったら、あとから公開できる。
- **引数の種類は登録のときに指定する**：指定しなければ、`SQRT` のような値を1つ取る関数もすべて「範囲が渡されたら `#VALUE!`」を自分で書くことになる。書き忘れると、範囲がどう扱われるかが関数ごとにばらばらになる。
- **エラーを受け取るかは登録のときに指定する**：インターフェースを分けると種類が増える。引数の個数と同じく、関数の外から見える性質なので、同じ場所で指定する。
- **関数名は計算するときに探す**：式を入れた順番と関数を登録した順番に関係なく、同じ結果になる。
- **範囲は写しにする**：関数がセルに触れないので、3.8 の計算の順番と循環参照の判断、関数を呼ぶ前のエラーの確認が、関数の作り方に関係なく守られる。写しは不変なので、並列化（3.8）の土台にもなる。
- **テーブルとグループを型で分ける**：グループは「名前で集めたセルの集まり」で、並びは持たない。順序を作ると、本来ない意味を持たせることになる。データベースでも、`ORDER BY` のない結果の順序は決まっていない。決まらないところを型で分けておけば、位置に意味がある関数は `Area` だけを受け付ければよく、グループを渡されたときの `#VALUE!` を書き忘れない。

## 3. 式の内部表現

### 3.1 構文木（AST）にする（2026-11-15）
今の逆ポーランド記法（RPN）をやめ、AST にします。

**理由**（RPN と比べて）
- `IF` で使わない側を計算しない、`AND`/`OR` を途中で打ち切る、`IFERROR` を作る、といった遅延評価が素直に書ける。RPN では計算する時点で引数がすべて計算済みになっていて、実現するにはジャンプ命令などが必要になる。
- 部品ごとに元の式の位置を持たせられるので、エラーの場所や値の由来（#40）、AI 向けの説明を作りやすい。
- 引数の数のチェック、「範囲は関数の引数にしか書けない」などの決まりのチェック、セル名を変えたときの式の書き換え、式の書き戻しが、木をたどる処理として書ける。
- 今の実装にある、カンマの部品を積んでおいて関数を計算する時点で数える処理や、`USE_LAST_RVALUE` などの仕掛けが不要になる。

**RPN の利点で失うもの、とその評価**
- 計算が再帰になる。ただし再帰の深さは1つの式の入れ子の深さだけで、人や AI が書く式では問題にならない。セルを5000個つなぐと起きる `StackOverflowError`（#32）は、セルからセルへの再帰が原因で、この選択とは関係ない。
- オブジェクトの数が増える。テーブルの列で同じ式を使う場合は、木が不変なので1つの木を共有できる。
- 速さが必要になったら、AST から RPN を作り出して実行する処理を後から追加できる（AST が正式な形で、RPN はそこから作るもの。今の RPN をそのまま残すわけではない）。

### 3.2 `FormulaParser` の書き直しの範囲
| 段階 | メソッド | AST にした場合 |
|---|---|---|
| 字句に分ける | `split` | 大部分を流用する（下の手直しが必要） |
| 正しさのチェック | `checkInfixNotation` と補助のメソッド | なくなる。AST を組み立てる処理がチェックを兼ねる |
| RPN への変換 | `infixToRPN` と補助のメソッド | AST を作る解析処理（再帰下降または Pratt パーサー）に置き換える |

`split` の手直し：
- 単項の `+`/`-` の判定は、解析処理の側に移す（#4 もこの周辺）。
- 関数が登録されているかの確認（`funcFactory.hasFunction`）は、解析より後に移す（#6、#21）。
- トークンのパターンを試す順番を見直す（#9、#10）。
- 戻り値を `Token` の並びにし、元の式の中の位置を持たせる。

（2026-11-22 に追記）この手直しは、`split` を書き換えずに、`split` を元にした別のメソッド `tokenize` として作った。`split` は今の計算処理（RPN）が使っているので、AST に移るまで残す。`tokenize` は数値を `MathContext` で丸めず、`%` も字句として扱う。読めない文字があると、その位置を持つ `FormulaException` を投げる。

**移行のしかた**：作り直している間だけ、今の計算処理と新しい計算処理を並べ、同じ式を両方で計算して結果を比べるテストに使います。結果が違ったところは、「新しい実装の誤り」か「今の不具合を直した結果」のどちらかです。新しい実装がそろったら、古い計算処理は削除します。

### 3.3 名前（2026-11-15）
役割が変わるので、`Element` という名前は使いません。

| 名前 | 公開 | 内容 | 今のどこに当たるか |
|---|---|---|---|
| `Value` | 公開 | セルの値、計算結果 | `Element` の値の部分 |
| `ErrorKind` | 公開 | エラーの種類 | `Element.ErrorType` |
| `Token` | 内部 | 字句に分けた結果の1つ（種類・文字列・元の式の中の位置） | `split` が返す `Element[]` の要素 |
| `Expr` | 内部 | 解析したあとの式（木の節） | `infixToRPN` が返す `Element[]` 全体 |
| `BinaryOp` / `UnaryOp` | 内部 | 演算子 | `Element.Operator` |
| `Formula` | 内部（公開は未決定、4.5） | 元の式の文字列と、解析した結果（`Expr` か誤り）の組（3.6） | `Cell` の `_formula` と `_formulaRPN` |

**理由**
- `Element` は「何かの要素」という意味しかなく、値か式の部品かが名前から分からない。それが今の混乱の一因になっている。
- `Token` は字句解析の結果を表す一般的な名前で、Java の開発者や AI が役割を推測できる。
- 木の節を `Node` ではなく `Expr` と呼ぶのは、Picosheet の式の言語には文がなく、すべての節が「計算すると値になる式」だから。
- 今の `Operator` には、括弧・カンマ（字句の種類で、木を組み立てたあとは消える）と `USE_LAST_RVALUE`（RPN 用の仕掛け）が混ざっている。それらを除くと、残るのは二項演算子と単項演算子で、使われる場所が違うので型を分ける。

`Expr` の形：

```java
sealed interface Expr {
    record Literal(Value value)              implements Expr {}
    record CellRef(String name)              implements Expr {}
    record GroupRef(String name)             implements Expr {}
    record TableRef(String name /* 範囲 */)   implements Expr {}
    record Unary(UnaryOp op, Expr operand)   implements Expr {}
    record Binary(BinaryOp op, Expr l, Expr r) implements Expr {}
    record Call(String fn, List<Expr> args)  implements Expr {}
}
```

**`Value` と `Expr` の関係**：`Value` は `Expr` を継承しません。式の部品の1つである `Expr.Literal` が `Value` を1つ持つ関係（has-a）です。
- `Value` は公開、`Expr` は内部なので、継承すると内部の型が公開APIに出てしまう（今の `Element` と同じ問題になる）。
- セルの値や計算結果の `Value` のほとんどは、式の中に書かれたものではない。
- `Value.Error` は計算の結果としてだけ生まれる値で、式にリテラルとして書くものではない。

### 3.4 比較演算子は二項演算子として左から順に計算する（2026-11-15）
今の Picosheet は `1<x<9` を `1<x AND x<9` として計算しますが、これをやめて、Excel と同じく `(1<x)<9` として計算します。
AST では比較も `Expr.Binary` の1つになり、連続比較のための特別な節も `USE_LAST_RVALUE` も不要になります。

**経緯と理由**
- 最初は、連続比較を書けないようにする（`INVALID_FORMULA` にする）案を選んだ。その後、1.2 の方針に合わせて、Excel と同じ意味にすることにした。
- Excel では `=1<5<3` が `(1<5)<3` → `TRUE<3` → `FALSE` になる。Excel では論理値は数値より大きいとして比べるので、`1<x<9` は x がいくつでも `FALSE` になる。
- 連続比較をシート単位のオプションで使えるようにする案も検討した。しかし、`MathContext`（精度を変えるだけ）と違って式の意味（文法）が変わるので、式をコピーすると意味が変わる、式だけを見ても意味が分からない、オプションを変えたら式を解析し直す必要がある、といった問題がある。そのため採用しない。

**注意**
- `1<x<9` はエラーにならずに `FALSE` を返すので、範囲の判定のつもりで書いてしまうおそれは残る。AI_REFERENCE.md に「範囲の判定は `AND(1<x, x<9)` と書く」と明記する。
- Excel と同じ結果にするには、型の違う値どうしの比較も Excel に合わせる必要がある（1.2 の表）。
- 範囲の判定を短く書きたい要望が出たら、オプションではなく `BETWEEN(x, 下限, 上限)` のような関数を用意することを先に検討する。

### 3.5 Java 21 以上を対象にする（2026-11-22）
`pom.xml` の対象を Java 17 から Java 21（LTS）に上げました。

**理由**
- `Value`、`Token`、`Expr` は sealed interface なので、`switch` のパターンマッチング（`case Expr.Binary b -> ...`）で種類ごとに処理を書けば、種類の漏れをコンパイラが見つけられる。この機能は Java 21 で正式になり、Java 17 ではプレビューとしてしか使えない。
- 0.2.0 はまだ公開していないので、対象のバージョンを上げても困る利用者はいない。

### 3.6 セルの式は `Formula` として持つ（2026-11-24）
セルは、元の式の文字列と、解析した結果を組にした `Formula` を1つだけ持ちます。今の `Cell` の `_formula`（文字列）と `_formulaRPN` は、作り直しが終わったら `Formula` のフィールド1つになります。

```java
sealed interface Formula {
    String source();                                         // 利用者が書いた式の文字列（そのまま）
    record Parsed(String source, Expr expr) implements Formula {}
    record Invalid(String source, int position, String message) implements Formula {}
}

// FormulaParser の入口。例外を投げず、読めなかった式は Invalid として返す
static Formula makeFormula(String formulaString) {
    try {
        return new Formula.Parsed(formulaString, parse(tokenize(formulaString)));
    } catch (FormulaException e) {
        return new Formula.Invalid(formulaString, e.getPosition(), e.getMessage());
    }
}
```

- `Formula` は、利用者が書いた式の文字列をそのまま持つ。式を表示・保存するときは、この文字列を使い、AST から作り直さない。
- 読めなかった式も `Formula`（`Invalid`）として持ち、誤りの位置と説明を残す。
- `makeFormula` の引数は式の文字列だけにする。`tokenize` は数値を丸めず、関数が登録されているかも確かめないので、`MathContext` も `FunctionFactory` も要らない。
- `tokenize`（字句に分ける）と `parse`（`Token` から `Expr` を組み立てる）は、`FormulaParser` の内部のメソッドとして分け、それぞれ単体でテストする。
- 関数が登録されているかは `makeFormula` では確かめない。`hoge(1)` も `Parsed` になり、登録されていない関数は、式をセルに設定するときか計算するときに見つける（Excel では計算した結果が `#NAME?` になる）。
- `Formula` は不変にする。セルの式を変えるときは `Formula` を丸ごと入れ替える。

**理由**
- **書いたとおりの式を残す**：AST には書き方の情報が残らない。空白は字句に分けるときに捨て、`true` と `True` はどちらも `Value.Bool(true)` に、`3.` と `.5` は数値の値だけになり、括弧は木の形に置き換わる。AST から式を作り直すと、利用者の書いた式と違う形になる。
- **Cell がなくても式を解析できる**：今は式を解析するのに、`Sheet`、`Book` とのつながりと、`MathContext`、`FunctionFactory` が要る。`Formula` を独立した型にすれば、式をセルに入れる前に誤りとその位置を確かめたり、ブックを作らずに解析処理をテストしたりできる。
- **読めなかった式を型で表せる**：フィールドで持つと、「AST が null なら誤りの情報がある」といった決まりを `Cell` のあちこちで守る必要がある。sealed interface の `Parsed` と `Invalid` にすれば、どちらの状態かが型で分かり、扱い漏れはコンパイラが見つける。
- **文字列と解析結果が食い違わない**：今の `Cell.setFormula` は、`_formula` を新しい式に変えたあと、`split` が失敗すると `_formulaRPN` を変えずに戻るので、前の式の RPN が残る。不変の `Formula` を丸ごと入れ替えれば、こうした食い違いは起きない。
- **式についての処理を1か所に集める**：参照している名前の一覧や、セルの名前を変えたときの式の書き換えは、セルではなく式についての処理なので、`Formula` の側に置ける。今は `_formula` を `Cell`、`PlainCell`、`TableCell` のそれぞれで扱っている。

**注意**
- セルの名前を変えたときに式を書き換える場合も、AST から作り直さず、`Token` の位置を使って元の文字列の参照の部分だけを差し替える。こうすれば、書き方はそのまま残る。
- `Formula` を利用者に公開するかは未決定（4.5）。公開する場合、`FormulaParser` はパッケージの内部のクラスなので、入口は `Formula.parse(formulaString)` のように `Formula` の側に置き、中で `FormulaParser` を呼ぶ。

### 3.7 `Expr` は元の式の中の位置を持つ（2026-11-25）
`Expr` のどのレコードも、元の式の中の位置（0始まり）を `position` として持ちます。位置は、その部分の木の先頭の字句の位置です。

```
(1+2)*3
Binary(*)      … 0  （左の被演算子が括弧で始まるので、その左括弧の位置）
  Binary(+)    … 1
    Literal(1) … 1
    Literal(2) … 3
  Literal(3)   … 6
```

- 二項演算は、演算子の記号の位置ではなく、左の被演算子の先頭の位置を持つ。
- 前置の単項の `+` と `-` は、演算子の位置を持つ。後置の `%` は、被演算子の先頭の位置を持つ。
- 関数は、関数名の位置を持つ。
- 括弧は木に残らない。括弧で始まる部分の木は、その左括弧の位置を持つ。式全体が括弧で囲まれている場合は、内側の木の位置になる。
- 位置は先頭だけを持ち、範囲（終わりの位置）は持たない。

**理由**
- **計算する処理より前に決める**：位置を足すと `Expr` の全レコードと、それを作る処理・テストが変わる。計算する処理（`Expr` → `Value`）を書いた後だと、直す量が増える。
- **エラーの場所を示せる**：計算した結果がエラー値になったとき、式のどの部分で起きたかを、エラー値や説明に含められる（4.4、#35）。人や AI が原因を探す助けになる。
- **先頭の位置だけで足りる**：式を書き換える処理は `Token` の位置を使う（3.6）。`Expr` の位置はエラーの場所を示すためのもので、範囲までは要らない。

**注意**
- 位置は式の意味には関わらない。ただし、record の `equals` は位置も比べるので、書き方（空白など）が違えば、同じ意味の式でも `Expr` は等しくならない。
- テストは分ける。木の形を確かめるテスト（`FormulaParserParseTest`）は、位置をすべて0にした木（テストの補助 `ExprShape`）で比べる。位置は `FormulaParserPositionTest` で確かめる。位置は、組み立てた式が正しいかとは関わりが薄く、問題の原因を探る助けのための情報なので、確かめるテストも分ける。

### 3.8 計算は3つの役割に分け、セルの間では再帰を使わない（2026-11-25、#32）
計算する処理を、次の3つに分けます。

| 役割 | 内容 |
|---|---|
| 式の計算 | `Expr` と「参照から値を得る口」を受け取り、`Value` を返す。ほかのセルは計算しない。セルの状態を知らず、副作用を持たない |
| 参照から値を得る口 | 名前からセルを探し、セルの状態を見て値を返す。範囲（グループ・テーブル）は値の並びにする。参照先が「計算必要」なら `NotYetCalculated` を、「計算中」なら循環参照を知らせる例外を投げる |
| 再計算 | 「計算必要」のセルを集め、計算する順番を決め、自分で持つスタックを使って計算する |

式の計算の中の再帰は、1つの式の入れ子の深さまでしか深くなりません（3.1）。セルからセルへは、Java の再帰を使いません。

**再計算の手順**
1. **集める**：値や式を変えたセルから、参照の表（参照されている側から参照している側への表。今の `Resolver` の `_references`）を幅優先探索でたどり、「計算必要」のセルを集める。
2. **数える**：集めたセルそれぞれについて、集めたセルの中にある参照先の数を数える。集めたセルごとに参照しているセルをたどり、相手の数を1増やす。
3. **並べる**：Kahn のアルゴリズムで順番を決める。最後まで順番に入らなかったセル（参照の表で循環しているセルと、その先のセル）は「残り」とする。
4. **積む**：残りを先に積み（スタックの下）、その上に、Kahn のアルゴリズムの順が上から出てくるように積む。
5. **計算する**：次のループで計算する。

```java
while (!stack.isEmpty()) {
    Cell cell = stack.peek();
    if (cell.getStatus() != REQUIRE_CALCULATION && cell.getStatus() != UNDER_CALCULATION) {
        stack.pop();                                  // もう計算済み
        continue;
    }
    cell.setStatus(UNDER_CALCULATION);
    try {
        cell.setValue(evaluator.evaluate(cell.formula().expr(), lookup));
        cell.setStatus(CALCULATED);
        stack.pop();
    } catch (NotYetCalculated e) {
        stack.push(e.cell);                           // 先に参照先を計算する。cell は計算中のまま待つ
    } catch (CircularReferenceFound e) {
        // スタックの e.cell から上が循環しているセル。循環参照のエラーにして取り除く
    }
}
```

- 順番に入ったセルは、参照先がすべて先に計算されるので、`NotYetCalculated` は起きない。
- 順番に入ったセルは、残りに依存しない（残りに依存するセルは、それ自体が残りに入る）。そのため、残りをスタックの下に置くだけで、2つを分けて扱う処理は要らない。
- `NotYetCalculated` が起きて計算をやり直すのは、残りのセルだけになる。1つのセルがやり直すのは、多くても「まだ計算していない参照先の数」回まで。

**循環参照の扱い**
- 循環しているかは、参照の表ではなく、計算するときに実際に読んだ参照で判断する。`A1` = `IF(TRUE, 1, A2)`、`A2` = `A1+1` は、参照の表では循環しているが、A1 は A2 を読まないので循環にならず、A1=1、A2=2 になる。Excel で確かめた結果と同じ（2026-11-25。エラーにも警告にもならなかった）。
- 循環しているセルは、循環参照のエラーにする。Excel は警告を表示して前の値を残すが、Picosheet はこれに合わせない（1.2 の表）。
- 循環の外から、循環しているセルを参照しているセルは、実際に読んだ場合だけエラーを受け取る。`B1` = `IF(TRUE, C3, D3)` で D3 が循環している場合、B1 は C3 の値になる。`IF(FALSE, C3, D3)` なら循環参照のエラーになる。
- 循環しているかどうかは、値によって変わる（上の `TRUE` を `FALSE` にすると循環になる）。これも Excel と同じ。

**理由**
- **長くつながったセルで `StackOverflowError` にならない**：#32 の原因は、セルの計算の中で参照先のセルを再帰で計算すること（今の `Calculator.recalcIfRequired`）。集める、並べる、計算するの3つとも再帰を使わないので、つながったセルの数に上限がなくなる。行番号の列（`=一つ上のセル+1`）のような長い鎖は、ふつうに使われる。
- **再帰との違いは、途中の状態を置く場所**：再帰で書いても、計算する順番と循環の見つけ方は同じになる。違うのは、別のセルが必要になったときに、式の途中の状態（`+` の左の値など）を Java の呼び出しのスタックに置くか、捨てて最初からやり直すか。自分で持つスタックにはセルしか置けないので、やり直しの無駄と引き換えに、深さの制限をなくしている。スレッドのスタックを大きくする方法は、上限を延ばすだけなので採らない。式の計算もスタックマシンにすれば途中の状態を置けるが、AST にした理由（3.1）と逆の方向になるので採らない。
- **ふつうの計算でやり直しを起こさない**：順番を決めずにスタックに積むと、参照先より先に参照元を計算しようとして、循環がなくてもやり直しがよく起きる（行番号の列の一番上を変えると、最悪で鎖の長さだけやり直す）。Kahn のアルゴリズムで順番を決めておけば、やり直しが起きるのは、参照の表で循環している部分（まれな場合）だけになる。
- **実際に読んだ参照で循環を判断する**：1.2 の方針どおり、Excel と同じ結果にするため。参照の表だけで判断すると、`IF` の使わない側を通る循環もエラーになり、Excel と違う結果になる。
- **「まだ計算していない」は値ではなく例外で知らせる**：`Value` の1種類にすると、`IFERROR` がエラーとして受け取って計算を終えてしまうおそれがあり、すべての演算子と関数で特別扱いが必要になる。セルの値として残るおそれもある。例外なら、途中の演算子や関数を何もせずに通り抜けて再計算の処理まで戻る。
- **時間は O(V + E)**：V は「計算必要」のセルの数、E はその間の参照の数。集める、数える、並べるの3つは、どれも O(V + E) で、各セルを1回ずつ計算するのと同じ程度。ブック全体の順番を覚えておく方法は、式を変えるたびに直す処理が要るので、測って問題になるまでは採らない。
- **並列化の土台になる**：式の計算に副作用がなく、`Expr` と `Value` は不変なので、互いに依存しないセルは別々のスレッドで計算できる。Kahn のアルゴリズムで決めた順番を、そのまま並列化の土台にできる。

**注意**
- 範囲の参照は、範囲をセルに展開せず、グループやテーブルを1つの節として扱う。展開すると、累計の列（各行で先頭から自分の行までを `SUM` する）などで E が行数の2乗に比例する。
- 範囲の中に計算していないセルが複数ある場合、参照から値を得る口はそれらをまとめて返す。1つずつ返すと、その数だけやり直す。
- 参照の表には、`IF` の使わない側の参照も含める。順番は必要より広めに決まるが、結果は変わらない。
- 例外は、スタックトレースを作らない（`RuntimeException` の `writableStackTrace` を `false` にする）。パッケージの外には出さない。循環参照を知らせる例外は、公開している `CircularReferenceException` と別のものにする。
- 今の `Resolver.getReferencingCellsRecursive` も再帰で参照の表をたどっているので、長い鎖では集める段階で深くなる。手順 1 で、再帰を使わない形に置き換える。
- 並列化は、今は作らない。1つのセルの計算は短く、スレッドに分ける手間のほうが大きくなりやすい。また、行番号の列のような鎖は並列化しても速くならない。まとめて値を入れてから計算する API（#27）ができてから、測って決める。それまでは、式の計算で共有の状態を変えないことだけを守る（#31）。関数のインスタンスと `FunctionFactory` が状態を持たないかも確かめる。
- テストで、循環のないブックではやり直しが0回になることを確かめる。順番に入ったセルで `NotYetCalculated` が起きたら、順番の決め方の不具合。
